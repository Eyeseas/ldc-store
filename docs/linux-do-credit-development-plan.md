# Linux DO Credit 支付接入开发计划

> 状态：开发中（本地实现完成，待官方测试模式与发布验收）
> 制定日期：2026-08-02
> 最近更新：2026-08-03
> 依据：[官方 API 文档](https://credit.linux.do/docs/api)、[官方源码快照](https://github.com/linux-do/credit/tree/f9026267704133be7a700be9e5f702c5dfee471e)、[本仓库 API 核对记录](./linux-do-credit-api.md)
> 目标版本：下一次支付集成迭代

## 1. 目标与技术决策

本次迭代需要在不中断现有支付的前提下完成四件事：

1. 保留现有 `type=epay` 易支付兼容流程，作为迁移期回退路径。
2. 新增 `type=ldcpay` 原生流程，使用 Ed25519 对发起支付请求签名。
3. 收紧查询、回调和退款实现，使其与现行官方契约一致。
4. 移除任何将 `LDC_CLIENT_SECRET` 发送到浏览器的路径。

采用渐进迁移：先修复凭证泄露风险，再增加协议抽象与原生协议，最后在测试模式和生产小流量验证后切换默认值。第一版不接入商户分发和用户余额统计，因为它们不属于自动发卡的核心链路。

## 2. 开发前实现与差距

| 能力 | 当前实现 | 现行官方能力 | 处理决定 |
| --- | --- | --- | --- |
| 发起支付 | 仅 `epay` + MD5 | `epay` + MD5；`ldcpay` + Ed25519 | 保留 `epay`，新增 `ldcpay` |
| 订单级回调地址 | 请求携带 `notify_url`、`return_url` | 订单级地址优先，应用配置兜底 | 当前行为正确，更新旧文档 |
| 订单查询 | 支持 `out_trade_no` 或 `trade_no` | 查询接口要求 `out_trade_no` | 移除未被官方契约支持的 `trade_no` 查询 |
| 支付回调 | GET、MD5 验签、金额与商户校验、幂等处理 | GET、易支付格式 MD5 签名、返回 `success` | 保留流程并强化恒定时间验签和运行时校验 |
| 退款 | `client`、`proxy`、`disabled` 三种模式 | 服务端 POST `/epay/api.php`，要求全额退款 | 删除 `client` 模式；只允许服务端直连、代理或禁用 |
| 密钥管理 | `client` 退款会把 Secret 返回浏览器 | Client Secret 和 Ed25519 私钥均属于服务端凭证 | 列为 P0，禁止进入客户端、日志或错误响应 |
| 订单协议追踪 | 数据库仅记录支付方式 `ldc` | 迁移期会同时存在 `epay`、`ldcpay` 订单 | 为订单记录 `payment_protocol` |
| 对账 | 结果页会按业务单号查询远端状态 | 查询可作为回调兜底 | 增加明确的失败分类、重试和晚到支付处理 |

## 3. 目标模块边界

调用方只依赖统一的支付模块接口，不接触协议字段、签名细节或密钥：

```ts
type PaymentProtocol = "epay" | "ldcpay";

interface LdcPaymentGateway {
  createPaymentForm(input: CreatePaymentInput): PaymentFormData;
  queryOrder(outTradeNo: string): Promise<RemoteOrder | null>;
  refund(input: RefundInput): Promise<RefundResult>;
  verifyNotification(input: URLSearchParams): VerifiedNotification;
}
```

建议将当前 `lib/payment/ldc.ts` 拆为 `config`、`signatures`、`schemas`、`gateway` 四个内部文件，并继续通过 `lib/payment/ldc/index.ts` 暴露单一入口。不要让 Server Action 或 Route Handler 自行拼装签名参数。

新增环境变量：

| 变量 | 用途 | 初始默认值 |
| --- | --- | --- |
| `LDC_PAYMENT_PROTOCOL` | `epay` 或 `ldcpay` | `epay` |
| `LDC_ED25519_PRIVATE_KEY_PKCS8_BASE64` | Base64 编码的 PKCS#8 Ed25519 私钥，仅 `ldcpay` 使用 | 无 |
| `LDC_REFUND_MODE` | `server`、`proxy` 或 `disabled` | `disabled` |

应提供密钥生成脚本，输出两项内容：供部署环境使用的 PKCS#8 私钥 Base64，以及供 Linux DO Credit 控制台上传的 32 字节 Ed25519 公钥 Base64。脚本不得输出或写入项目文件之外的真实生产凭证。

## 4. 实施阶段

### P0：阻断客户端凭证泄露（0.5-1 人日）

- [x] 将退款默认模式改为 `disabled`。
- [x] 删除 `getClientRefundParams`、`getClientRefundData` 和客户端自动提交退款页面。
- [x] 删除前端可见类型中的 `key` 字段以及对应测试夹具。
- [x] 将退款入口限制为服务端直连或显式配置的可信代理。
- [x] 更新 README、部署文档和环境变量示例，不再推荐 `client` 模式。
- [x] 增加构建产物扫描，确认 Client Secret、私钥和测试密钥不会进入客户端 bundle。

验收标准：浏览器网络响应、页面源码和客户端 bundle 中均不存在 `LDC_CLIENT_SECRET`；未配置服务端退款能力时，后台明确显示退款不可用。

### P1：统一支付模块与配置校验（1-1.5 人日）

- [x] 建立统一输入、输出和错误类型，隔离 EasyPay 与 LDC 原生协议字段。
- [ ] 用 Zod 在启动或首次调用时校验网关 URL、协议、Client ID、Secret 和私钥配置。
- [x] 新增 `orders.payment_protocol`，已有订单回填为 `epay`。
- [x] 统一金额格式为两位小数字符串，禁止浮点数直接参与签名或金额比较。
- [x] 使用确定性的 ASCII 字段排序，不依赖运行环境的 `localeCompare`。
- [ ] 为网络错误、平台拒绝、响应格式错误和订单不存在建立可区分的错误码。

验收标准：现有 `epay` 行为不变；业务层不再读取协议专用字段；错误日志不包含 Secret、私钥、完整签名或带 `key` 的 URL。

### P2：接入 `ldcpay` 与 Ed25519（1-1.5 人日）

- [x] 按官方规则对所有非空字段按 ASCII 排序并拼接。
- [x] 在规范化参数串末尾追加 Client Secret。
- [x] 使用 Ed25519 私钥签名，并将签名结果编码为标准 Base64。
- [x] 使用原生字段：`client_id`、`type=ldcpay`、`out_trade_no`、`money`、`order_name`、`notify_url`、`return_url`、`sign`。
- [x] 始终以 POST `application/x-www-form-urlencoded` 提交 `/epay/pay/submit.php`，不依赖官方页面中尚未被当前服务端实现支持的 JSON 描述。
- [x] 保留 `epay` 构造器，通过 `LDC_PAYMENT_PROTOCOL` 选择协议。
- [ ] 增加密钥生成、控制台公钥配置和密钥轮换说明。

验收标准：官方测试模式能够打开支付确认页；篡改任意签名字段会被平台拒绝；相同输入生成的签名可被官方实现验证。

### P3：回调与对账加固（1-1.5 人日）

- [x] 用运行时 Schema 解析回调，不接受未知状态或格式异常金额。
- [ ] 兼容当前上游源码使用的 EasyPay 字段集与 MD5 回调签名；在官方测试模式中确认 `ldcpay` 的实际通知契约后再锁定实现。
- [x] 使用 `crypto.timingSafeEqual` 比较签名，并兼容十六进制大小写。
- [x] 校验 `pid`、`trade_status`、业务单号、远端流水号、支付方式和金额。
- [x] 查询只使用 `out_trade_no`；对 404、`code=-1`、超时、Cloudflare 页面和非 JSON 响应分别处理。
- [x] 定义晚到支付策略：本地已过期但远端成功时不得静默返回成功，必须进入人工处理、自动补发或自动退款中的一种确定状态。
- [x] 为回调重试保持幂等，数据库更新与卡密发放继续放在同一事务中。

验收标准：重复回调不会重复发货；金额或商户不匹配不会改变订单；回调暂时失败时返回非 200/非 `success` 以触发平台重试；晚到支付可追踪且不会形成“已扣款但无订单处理记录”。

### P4：服务端退款与状态一致性（1-1.5 人日）

- [x] 退款请求只在服务端构造，使用原支付流水号和原始全额金额。
- [x] 对平台 `code=1`、业务失败、HTTP 失败、超时和未知响应分别建模。
- [ ] 对超时等不确定结果先查询远端状态，禁止管理员仅凭页面提示手工标记成功。
- [x] 平台退款成功后，在单个数据库事务中更新订单和卡密状态。
- [x] 重复审批同一退款必须幂等，并记录管理员、请求时间、远端响应类别和最终状态。
- [x] 代理模式限定 HTTPS 地址并配置超时；代理不得记录或返回 Client Secret。

验收标准：任何退款路径都不会把凭证发送给浏览器；本地 `refunded` 状态必定有可验证的平台成功结果；失败或未知结果不会回收卡密。

### P5：文档、观测与发布（1 人日）

- [x] 更新 README、中文 README、部署文档、Docker 文档和环境变量示例。
- [ ] 为支付创建、回调、查询和退款增加不含敏感信息的结构化日志。
- [ ] 记录协议、业务单号、远端流水号、耗时和结果类别，禁止记录完整请求体。
- [ ] 在官方测试模式完成端到端验证。
- [ ] 先在预发布环境启用 `ldcpay`，生产环境继续使用 `epay`。
- [ ] 生产验证稳定后再将默认协议改为 `ldcpay`，至少保留一个版本的 `epay` 回滚能力。

验收标准：运维人员只看日志即可区分平台拒绝、网络故障和本地事务失败；切回 `epay` 不需要数据库回滚。

## 5. 测试矩阵

### 单元测试

- MD5 与 Ed25519 官方签名向量。
- 参数顺序、空字段、Unicode 商品名、`10`/`10.00` 金额规范化。
- 签名篡改、错误密钥、非法 Base64、错误私钥格式。
- 配置缺失、协议非法、网关 URL 非 HTTPS。
- 回调恒定时间验签和大小写兼容。

### 集成测试

- `epay` 与 `ldcpay` 支付表单字段及跳转地址。
- 回调缺参、商户不匹配、金额不匹配、重复通知和并发通知。
- 查询成功、处理中、不存在、404、超时、Cloudflare HTML 和非法 JSON。
- 退款成功、重复退款、余额不足、金额不一致、超时后对账。
- 数据库事务失败时订单与卡密同时回滚。

### 官方测试模式验收

1. 发起一笔 `ldcpay` 测试订单并完成认证。
2. 确认同步返回页可恢复订单状态。
3. 记录并确认 `ldcpay` 异步通知的实际字段、`type` 值和签名算法。
4. 确认异步回调只发放一次卡密。
5. 用 `out_trade_no` 查询并比对流水号、金额和状态。
6. 执行全额退款并确认本地订单、卡密和平台状态一致。
7. 重放支付回调和退款操作，确认全链路幂等。

## 6. 发布门槛与回滚

发布前必须满足：

- P0 安全项全部完成。
- 支付模块相关单元与集成测试全部通过。
- 官方测试模式完整走通支付、回调、查询和退款。
- 代码扫描确认客户端产物和日志中没有支付凭证。
- 预发布环境至少完成一次异常演练：回调超时、重复回调、退款超时。

回滚只切换 `LDC_PAYMENT_PROTOCOL=epay` 并重新部署。数据库中的 `payment_protocol` 保留历史值，查询、回调和退款继续按订单记录处理，不删除已经创建的原生协议订单。若退款链路异常，立即将 `LDC_REFUND_MODE=disabled`，保留退款申请记录并转人工处理。

## 7. 工作量与顺序

| 顺序 | 阶段 | 预计工作量 | 前置条件 |
| --- | --- | --- | --- |
| 1 | P0 凭证安全 | 0.5-1 人日 | 无 |
| 2 | P1 模块与配置 | 1-1.5 人日 | P0 |
| 3 | P2 Ed25519 原生支付 | 1-1.5 人日 | P1、控制台可配置公钥 |
| 4 | P3 回调与对账 | 1-1.5 人日 | P1 |
| 5 | P4 服务端退款 | 1-1.5 人日 | P0、可用服务端网络或可信代理 |
| 6 | P5 发布准备 | 1 人日 | P2-P4 |

总计约 6-9 人日，不包含等待 Linux DO Credit 测试账号、Cloudflare 放行或代理部署的时间。P0 应独立优先发布，不等待原生协议开发完成。

## 8. 待确认事项

- Linux DO Credit 控制台是否已为当前应用开放公钥和测试模式配置。
- `ldcpay` 的生产回调是否继续使用 `type=epay` 和 MD5；官方页面未明确，当前上游源码如此实现，必须以测试模式实测为准。
- 生产部署环境能否直接访问 `/epay/api.php`；若仍被 Cloudflare 拦截，需要先部署可信服务端代理。
- 晚到支付采用自动补发、自动退款还是进入人工审核。
- Ed25519 私钥由现有部署平台密钥库管理，还是接入独立的 Secret Manager。
